# Walkthrough: build and process a batch of records

This walkthrough follows [example-workload.js](example-workload.js) from start
to finish. It creates 100,000 records, processes them for 500 ms, and releases
the application reference before exiting. We will answer three questions:

1. Where does processing time go?
2. How much process and heap memory is present while records are being used?
3. How repeatable are those measurements?

We are not testing an optimization here. The final comparison runs the same
code twice to establish a reference.

## 1. Prepare one binary and one workload

Start in the repository root with PowerShell 7. Build the CLI using the
[README](../README.md). Commands below assume `v8-etw` is on PATH; otherwise
use `.\target\release\v8-etw.exe`.

For every step in this guide, use d8 built with the
[optional diagnostic patch](../patches/README.md). Stock d8 can run the sample
and support process comparisons, but it does not emit the activity and memory
events needed for this guide's `hotspots` and `composition` steps.

Preserve that build's executable, matching PDB and required snapshot file in
`C:\captures\matching-build`. Do not rebuild it during recording.

```powershell
$d8 = 'C:\captures\matching-build\d8.exe'
$work = (Resolve-Path .\docs\example-workload.js).Path
```

Read the workload before recording. It has two activities:

| Activity | Work | What remains afterward |
|---|---|---|
| `build-records` | Allocate the array, objects and record strings | `records` still refers to the array |
| `use-records` | Repeatedly read the records and accumulate a total | Records remain reachable until this activity ends |

The final `records = null` happens **after** the second activity. It does not
force GC or create a post-release observation window. We can study memory while
the batch is in use; this example cannot prove whether memory is reclaimed
after release.

**Checkpoint:** use this same binary and workload throughout. Expect two
activities, not a particular memory size or function count.

## 2. Record a reference and a diagnostic run

First record without ETW or memory probe flags:

```powershell
.\scripts\measure.ps1 -Executable $d8 -RuntimeArguments @($work) `
  -OutputDirectory C:\captures\reference-run
```

The helper creates run metadata, stdout/stderr logs and process memory samples.
Open `stdout.log`: it should contain begin/end markers for both activities,
followed by `runComplete: true`. Check exit code zero in `run.json`.

Next, in an **elevated PowerShell**, set `$d8` and `$work` again and record:

```powershell
.\scripts\capture.ps1 -Executable $d8 `
  -RuntimeArguments @('--enable-etw-stack-walking',
    '--no-enable-etw-by-custom-filter-only',
    '--trace-process-memory-etw', $work) `
  -OutputDirectory C:\captures\diagnostic-run\capture
```

This creates the same run files plus `capture.etl`. WPR starts before d8.
The workload's optional `d8.zoneMemoryMarker` calls emit ETW activity intervals;
memory probes add observations at their boundaries and during execution.

**Checkpoint:** both runs must complete both activities. Read `stderr.log` if
either fails. The diagnostic run adds overhead, so do not use its duration as
an uninstrumented performance result. See [run inputs](run-inputs.md) for the
files generated by these helpers.

## 3. Decode and check capture health

You no longer need elevation for analysis:

```powershell
$run = Get-Content C:\captures\diagnostic-run\capture\run.json -Raw |
  ConvertFrom-Json
v8-etw C:\captures\diagnostic-run\capture\capture.etl `
  --pid $run.ProcessId --output C:\captures\diagnostic-run\analysis `
  --symbols-dir C:\captures\matching-build --require-pdb d8.exe

$health = Get-Content C:\captures\diagnostic-run\analysis\summary.json -Raw |
  ConvertFrom-Json
$health | Select-Object complete, events_lost, buffers_lost
$health.metadata_errors
$health.property_errors
```

Proceed only with a complete decode, zero loss and empty error maps.
`--require-pdb` checks native attribution against the recorded build.

**Why new output paths?** A decode produces linked event, symbol and report
files. Partial replacement could mix different runs or destroy the reference.
The CLI currently has no overwrite option. Re-decode into `analysis-v2`, or
give a derived report a new filename such as `composition-v2.json`.
The `symbols` command can reuse decoded events, but its output files must be
absent; preserve previous outputs deliberately before regenerating them.

**Checkpoint:** healthy transport and matching symbols come before interpreting
costs. Do not disable a failed validation just to get a report.

## 4. Find the CPU work in `use-records`

```powershell
v8-etw hotspots C:\captures\diagnostic-run `
  --output C:\captures\diagnostic-run\cpu-hotspots.json
$cpu = Get-Content C:\captures\diagnostic-run\cpu-hotspots.json -Raw |
  ConvertFrom-Json -AsHashtable
$processing = $cpu.plans['use-records']
$processing.cpu_stack_samples
$processing.unresolved_leaf_samples
$processing.leaf_functions | Select-Object -First 5
$processing.inclusive_functions | Select-Object -First 5
```

Read the sample counts before the function list. Few samples give weak evidence;
many unresolved leaves mean attribution is incomplete.

- **Leaf:** where execution was observed at the sampled instant. JavaScript
  processing functions would be consistent with the loop in this activity.
- **Inclusive:** functions anywhere in those stacks, including callers. A
  runtime function appearing here does not mean all its samples were executing
  inside that function.
- **Worker work:** associated by time, not proof that the activity caused it.

Actual names depend on JIT tiering and symbol availability. If GC functions
appear, you have observed GC work during processing, not automatically a leak.
If they do not appear, sampling has not proved that GC cost was zero.
The lists show the top 100 functions; inclusive counts overlap.

You can also open `v8-etw tui C:\captures\diagnostic-run\analysis`: use Tab to
change sections and Up/Down, Right/Left to navigate Call paths. Quit with `q`.
The Activities tab shows composition and comparison reports as described below.

**Checkpoint:** identify a sampled processing cost and its coverage limitations.

## 5. Identify memory present while the records are used

```powershell
v8-etw composition C:\captures\diagnostic-run `
  --baseline C:\captures\reference-run `
  --output C:\captures\diagnostic-run\composition.json
$memory = Get-Content C:\captures\diagnostic-run\composition.json -Raw |
  ConvertFrom-Json -AsHashtable
$processing = $memory.plans['use-records']
$processing.entry
$processing.snapshot_peak
$processing.end
$processing.max_observed_snapshot_gap_ms
$processing.within_plan_baseline_runs
```

To explore the generated report interactively:

```powershell
v8-etw tui C:\captures\diagnostic-run\composition.json
```

In **Activities**, use Up/Down (or `j`/`k`) to select an activity. The composition
table compares entry, the activity's own observed peak and end. PgUp/PgDn scroll
the exact fields below it, including spaces, allocator gauges, natural GC
observations, sample gaps and reference runs. Missing values read `unavailable`;
a measured zero stays zero.

Entry is the first complete observation within the activity, peak is the
observation with the highest process private memory, and end is the last.
Compare those points **within `use-records`**. Then examine `build-records`
separately to understand the allocation stage.

Start with these fields:

| Field | Question it answers | What it does not prove |
|---|---|---|
| `process_private_bytes` | How much private commit does the process hold? | Which objects own all of it |
| `v8_heap_committed_bytes` | How much memory is committed to the active V8 heap? | How much is live application data |
| `v8_heap_accounted_used_bytes` | How much does heap accounting consider used? | An exact count of reachable record objects |
| `spaces` | Which heap spaces contain that accounting? | Object types or allocation call sites |
| `partition_alloc` | What native allocator backing is reported? | A disjoint amount to add to V8 heap totals |

The array and its records remain reachable throughout `use-records`. Memory
present at its end is therefore not surprising. A flat curve can mean the
batch was allocated before processing; a rising curve needs closer examination
of heap spaces, GC checkpoints and allocation behavior.

Other allocator fields may be zero or absent. Do not turn that into a cache
investigation unless your recording supports it. Reserved addresses, committed
backing and resident working set are different measurements; overlapping
gauges must not be summed into a new process total.

The reference samples provide an uninstrumented check for the same activity.
They are not expected to match the diagnostic snapshots exactly. Check gaps:
the short `build-records` phase may have very few process samples, while
`use-records` lasts long enough for more observations. A missed peak remains
possible. The companion `composition-samples.jsonl` preserves all snapshots.

**Checkpoint:** state what is present during processing, not what was reclaimed
after release. This example supplies no post-release window for the latter.

## 6. Check repeatability without inventing a candidate change

Record the same code twice, with probes off:

```powershell
.\scripts\measure.ps1 -Executable $d8 -RuntimeArguments @($work) `
  -OutputDirectory C:\captures\paired-runs\before-a
.\scripts\measure.ps1 -Executable $d8 -RuntimeArguments @($work) `
  -OutputDirectory C:\captures\paired-runs\after-a
```

Save this as `C:\captures\paired-runs\pairs.json`:

```json
{
  "performance": [
    {"id":"repeat-a","control":"before-a","candidate":"after-a"}
  ]
}
```

```powershell
v8-etw compare C:\captures\paired-runs `
  --output C:\captures\paired-runs\comparison.json
$comparison = Get-Content C:\captures\paired-runs\comparison.json -Raw |
  ConvertFrom-Json -AsHashtable
$comparison.plans['use-records'].paired_runs
$comparison.plans['use-records'].paired_metric_summary
$comparison.score_available
$comparison.gc_latency_available
```

```powershell
v8-etw tui C:\captures\paired-runs\comparison.json
```

The Activities comparison table shows median paired changes. Scroll its details
for pair-by-pair values, GC p50/p95/max, scope timings, observation counts and
exclusions. Use `m` to switch between composition and comparison when both reports
are present. A directory loads `composition.json` and `comparison.json`; passing
a report file directly supports any filename. Tab returns to other report views.

The manifest labels one run "candidate," but **nothing changed**. Differences
are observations of run-to-run variation, not an optimization.
Negative memory/CPU changes mean reductions in that pair. Missing observations
stay null. One pair cannot establish a reliable distribution.

This sample emits no score and we did not record separate GC-timing pairs:
both availability fields should be false. Its 500 ms processing loop is
time-bounded, not a throughput score; duration alone cannot tell you how many
record visits were completed.

**Checkpoint:** if identical code runs vary substantially, establish a better
reference before comparing a real change. Repeat in alternating order and keep
builds/unrelated work out of calibration.

## 7. Make a conclusion supported by this recording

A useful conclusion identifies:

- The sampled CPU work during `use-records`, with symbol coverage.
- The process and heap accounting while the batch remained reachable.
- Variation between the two uninstrumented runs.
- What remains unknown: exact live-object sizes, throughput, GC latency and
  memory reclamation after `records = null`.

If your next question is reclamation, add a separately marked post-release
phase to the **same application** and record its natural behavior. Do not force
GC just to make the curve fall. If testing a code change, keep the activities
and measurement contract comparable and collect enough repeated pairs.
